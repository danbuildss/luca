## Problem Statement

On-chain operators — people running wallets, autonomous agents, x402 payment flows,
and treasury operations on Base — have no reliable way to answer basic financial
questions: "What is revenue vs internal transfer?" "Why did treasury fall this week?"
"What did we spend through x402?" They're managing real money with no books.

The current workflow: checking block explorers, copying tx hashes into spreadsheets,
or doing nothing and guessing. This is not a hypothetical pain — it is what every
operator does today. The problem is not data availability (Base is fully public). The
problem is interpretation.

---

## Demand Evidence

- The founder is an on-chain operator with this problem personally. Real wallets.
  Real USDC. Real inability to answer "how much revenue came in this month?" without
  manual work.
- x402 payments and Base agent workflows are growing. Every new autonomous agent
  creates new wallet activity that needs classification.
- The "5 actual operators" target exists because there is a known community of people
  running on-chain businesses who will immediately recognize the problem.
- The demand signal that matters: an operator who corrects Luca's classification and
  sees it remember the correction next time. That's the moment they become a paying user.

---

## Status Quo

Current operator workflow:
1. Open Basescan or Alchemy dashboard
2. See a list of transactions with no context
3. Manually try to remember or look up what each counterparty is
4. Maybe copy to a spreadsheet, probably not
5. Give up and make financial decisions on intuition

Cost: hours per month for active operators. Zero auditability. Zero alerts for
anomalies. Zero understanding of counterparty patterns.

---

## Target User & Narrowest Wedge

**Target user (narrowest):** Solo or small-team operator running 3-10 Base wallets
with a mix of revenue, expenses, and autonomous agent activity. Not a DeFi trader.
Not a retail user. Someone whose wallets are doing business, not speculation.

**Narrowest wedge:** A daily brief delivered via Telegram that answers:
"Cash position. Yesterday's revenue. Yesterday's expenses. What Luca doesn't
understand yet."

That one message — received every morning — is the thing someone would tell their
friends about. It's also the thing that reveals every classification error and drives
corrections.

---

## Constraints

- V1: Base chain only. USDC + ETH only.
- No execution, no wallet signing, no trading. Read-only forever in V1.
- Hermes as the agent runtime — not a custom framework.
- VPS deployment, not serverless (Hermes gateway requires persistent process).
- SQLite for alpha (one user). PostgreSQL when adding users.
- Bankr installed as read-only Hermes skill — IP-locked to VPS.
- Telegram-first. Web app comes after the agent is working well.
- The founder uses it on their own wallets every day before asking anyone else to.

---

## Premises

All confirmed during session:

1. On-chain operators experience real, daily financial classification pain — not
   hypothetical.
2. The corrected financial graph is the moat, not the LLM. Corrections compound per
   user; a competitor cannot copy them.
3. Telegram is where on-chain operators actually are. It is the right first interface.
4. Base is the right starting chain — right ecosystem density, right operators.
5. Read-only is a viable business. Observability alone is worth charging for.

## Approaches Considered

### Approach A: Ship It Fast (Minimal Viable, Private)
Hermes profile + Telegram + SQLite + basic ingestion. LLM-first classification.
Corrections stored. No full deterministic rules layer yet. Private, for founder only.

- Fast to daily use (1-2 weeks)
- But: LLM-first is expensive, slow, wrong. Moat doesn't start building until
  deterministic rules exist.
- Rejected: Distribution problem unsolved. Finding 5 beta operators requires outreach.

### Approach B: Build It Right (Full Architecture First)
Full 20-stage Luca Core: 4-layer classification, corrections engine, monitoring,
alerts, briefs. All built correctly from day one.

- No rewrites. Moat starts immediately.
- But: 3 months to first daily use. High risk of building wrong rules before seeing
  real wallet behavior.
- Rejected: Too slow. YC application window doesn't wait.

### Approach C: Build In Public (Chosen)
See Recommended Approach below.

## Recommended Approach

**Build In Public: minimal Luca for the founder's wallets, posted publicly on X.**

The build sequence:

**Realistic Build Timeline**

**Weeks 1-2: Infrastructure (Stages 1-4)**
- Stage 1: SOUL.md + identity files locked. SOUL.md is the Hermes agent's personality
  and operational rules — defines who Luca is, what it will and won't do, and its
  financial worldview. "Locked" means committed to the repo; don't edit without intent.
- Stage 2: VPS provisioned, dedicated `luca` Linux user, Hermes `luca` profile created,
  gateway running as systemd service. SSH keys only, root SSH disabled.
- Stage 3: @AskLucaBot registered, Telegram webhook configured, owner's Telegram ID
  allowlisted. Goal: receive a test message from Luca.
- Stage 4: Bankr skill installed with read-only API key, IP-locked to VPS IP. Document
  the VPS IP as a critical config value — any server replacement requires re-issuing
  the Bankr key before go-live.

**Weeks 3-4: Wallets and Ingestion (Stages 5-6)**
- Stage 5: Register founder's Base wallets, assign roles (operations, treasury, personal,
  agent).
- Stage 6: Transaction ingestion via Alchemy Transfers API. Pull last 30 days on wallet
  add (backfill). Then: poll every 60 seconds for new activity. Deduplicate on tx_hash
  (idempotent). Normalize transfers: from/to, asset, amount, USD value, gas.
  Failure policy: if Alchemy is down during brief generation, send brief with stale-data
  warning. Retry ingestion for up to 10 minutes before marking sync as degraded.

**Weeks 5-6: Classification and Corrections (Stages 7-8)**
- Stage 7: 4-layer classification engine (in order):
  - Layer 1 (deterministic): Same-wallet transfers = internal_transfer. Gas payments = gas.
    Known x402 contracts = x402_income or x402_spend. Confidence: high.
  - Layer 2 (counterparty rules): Corrections the user has made. If "wallet 0x123 is CORTX
    revenue" was set, apply it. Confidence: high.
  - Layer 3 (pattern/protocol): Contract type, tx cadence, amount patterns, protocol
    fingerprints. Confidence: medium.
  - Layer 4 (LLM fallback): Only for unresolved transactions. Returns classification +
    reasoning + confidence. Batch unclassified txs and call once per sync, not per tx.
    Estimate: founder's wallets generate ~20-50 txs/day; LLM cost at batch level is
    manageable. Add a circuit breaker: if daily LLM spend exceeds $1, log and alert.
- Stage 8: Corrections. Two types, stored separately:
  - **Transaction correction:** "That specific tx was revenue, not an expense." Stored
    with tx_hash. Applied to that tx permanently. Does not create a rule.
  - **Counterparty rule:** "Payments from 0x123 are always CORTX revenue." Stored with
    counterparty address + classification. Applied deterministically: on every
    classification run, all counterparty rules for the wallet's known counterparties are
    loaded and applied during Layer 2. No truncation — if 20 rules exist, all 20 apply.
    Most recent rule for a given counterparty wins on conflict.
  User input method: natural language via Telegram, or `/correct <tx_hash> <category>`
  for precision. Corrections table schema:
  `(id, user_id, type[tx|counterparty], tx_hash?, counterparty?, classification,
  created_at, source_message)`. Corrections never expire. If Luca misapplies a
  counterparty rule, it is a code bug — log and alert.

**Weeks 7-8: Books and Daily Brief (Stages 9, 13 partial)**
- Stage 9: Books. Aggregate classified transactions into rolling buckets: revenue,
  expense, gas, internal_transfer, x402_income, x402_spend, refund, unknown. Query
  against books, not raw transactions.
- Stage 13 (brief only): Daily brief delivered at 8am operator timezone (set via
  `/timezone <tz>` Telegram command on first use; stored in users table). If no brief
  was sent in the past 25 hours, a watchdog cron fires a Telegram alert to the founder
  ("Luca brief watchdog: no brief sent in 25h. Check the gateway."). Daily brief format:

  ```
  Luca — Daily Brief

  Cash
  $8,432 USDC / 0.42 ETH

  Yesterday
  Revenue       +$620
  Expenses      -$184
  Gas           -$7.41
  Net           +$428.59

  3 wallets active.

  Attention
  • $240 payment to a new counterparty
  • $93 remains unclassified
  ```

  Financial categories in the brief map as follows: revenue and x402_income combine
  into "Revenue". expense and x402_spend combine into "Expenses". gas is shown
  separately. refund is shown as a positive line if material. internal_transfer and
  treasury are excluded from P&L (not income or expense). unknown is shown under
  "Attention" as the unclassified amount.

**Multi-user isolation:** Each user gets a separate SQLite database file (keyed by
telegram_id) in V1 alpha. The schema must be PostgreSQL-compatible from day one —
use standard SQL types, no SQLite-isms, foreign keys enforced. This makes the migration
a data-copy + connection-string change, not a schema redesign.

When the second user is invited to beta: run a migration script that creates PostgreSQL,
copies each SQLite database into user-scoped rows, and switches the connection string.
This is a multi-day task (migration script, testing, downtime window on VPS). Plan for
it in Month 3 before any beta invites go out. Do not add a second user to SQLite.

**Month 3: Build In Public**
- Post the daily brief on X. Real numbers from real wallets.
- Screenshot Luca catching an unusual payment. Screenshot a weekly report.
- Post "Luca classified this correctly for the first time after I corrected it."
- "Here's how much gas my agents spent this week."

**The operator acquisition flow:**
1. Operator on X sees Luca output and thinks "I need this for my wallets"
2. They DM the founder or comment
3. Founder gives them access (SQLite database created for them on onboarding)
4. They correct Luca → moat starts building for that user
5. They post their own Luca outputs → flywheel

**Distribution advantage over Approach A:**
- Operators find you. You don't hunt them.
- "Luca, give me my financial brief" is the best product demo in existence.
- Every public brief is a proof-of-work that builds trust before asking for wallet
  access.

**Month 4: Full architecture and beta**
- Complete monitoring engine (Stages 10-12): continuous wallet sync via Hermes cron,
  alert rules (large tx, new counterparty, spend spike, treasury floor, high unknown),
  alert delivery to Telegram.
- Full weekly and monthly report generation (Stage 13 complete).
- Reliability hardening (Stage 14): retries, stale-data detection, duplicate prevention,
  audit log.
- Private beta invite to 5 operators met through X (Stage 15).

## Open Questions

1. **How much of the founder's wallet activity is visible to post publicly?** On-chain
   data is already public, but Luca's interpretation reveals business context. What's
   the right level of transparency? (Suggestion: post the brief format and numbers,
   redact counterparty labels if sensitive.)

2. **What is the pricing model?** Not urgent for alpha, but the first operator beta
   should have a price attached. Even $49/month signals that this is a real product.

3. **When does the web app become necessary?** Current thesis: Telegram-first until
   the conversation interface feels limiting. Do NOT build the web app to look like a
   startup. Build it when operators ask for it.

## Success Criteria

| Metric | Threshold |
|---|---|
| Transaction ingestion completeness | Effectively 100% (no gaps) |
| Daily brief delivery reliability | Delivered every morning, never silent |
| Classification accuracy after 30 days | >80% correct on founder's wallets |
| Corrections remembered | 100% — if Luca forgets a correction, that's a bug |
| Cross-user financial leakage | Zero |
| Beta operators invited | 5 (from X operator DMs and direct outreach) |
| Beta operators actively correcting Luca daily | ≥3 within 60 days of their invite |
| X engagement on public briefs | At least one operator DM per week by month 2 |
| Luca used by founder daily | Required — if founder isn't using it, nothing else matters |

## Distribution Plan

**Channel 1: Build In Public on X**
Post Luca's actual output. Daily brief screenshots. Caught anomalies. Weekly reports.
"Here's what my wallets did this week, as understood by Luca." Target: Base/on-chain
operator community on X.

**Channel 2: Operator community direct**
Find 5 operators in the Base ecosystem who run wallets/agents/x402 flows. Reach
out directly with "I built a thing that classifies your on-chain activity — want to
try it?" The public briefs give you credibility for this outreach.

**Channel 3: YC application (target W27 batch)**
The design doc, the working agent, the operator briefs, and 5 real users are the
application. This is a stronger application than most of what YC sees.

**Deployment:**
- VPS: single server, systemd, Hermes gateway as service
- No CI/CD needed for V1 — it's one server
- Backup: encrypted daily, tested monthly

## What I Noticed About How You Think

- You said "we are not building Hermes with a Luca prompt." That's a product thesis,
  not a feature description. It tells you exactly what not to build and why. Most
  founders can't articulate that at Stage 0.
- You locked the design direction to "Mercury / Linear / Stripe restraint" and
  "monospace numbers" before writing a line of code. You're optimizing for trust and
  clarity, not excitement. That's the right call for financial infrastructure. It means
  you understand your user.
- The 20-stage build order is protective — you put "corrections" at Stage 8, before
  "briefs" at Stage 13, before "private alpha" at Stage 15. That's the right sequence.
  Most builders would skip corrections and wonder why users churn.
- "Silence is normal. Speak when something changed that matters." That's not an
  alert feature — that's a product philosophy. Write that on the wall.
